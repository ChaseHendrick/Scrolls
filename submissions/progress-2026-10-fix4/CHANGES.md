# AutoPipeline 0.1.4: what changed since 0.1.3

The earlier releases stay as they were: AutoPipeline 0.1.0 is submission `progress-2026-10` (branch `submission/progress-2026-10`, commit `faada83287d39bbd4c7fd88c7ab0e75f3f1ff284`), 0.1.1 is `progress-2026-10-fix1` (commit `153413691ec2ca794acdb3bf5784c0882a43e228`), 0.1.2 is `progress-2026-10-fix2` (commit `143c54b54804e17acbfdcf032217e6b3964f6ef4`) and 0.1.3 is `progress-2026-10-fix3` (commit `bd7d6cfcc9ac84bfdb3cc295d60f3b9c8696bbed`). This package, `progress-2026-10-fix4` (15 October 2026), is the whole of AutoPipeline 0.1.3 again with the fixes below. No earlier result changed.

## Remote render arguments for villa's current VC3D

villa commit ba2bf75 (pull request #1863, 12 October 2026) changed `vc_render_tifxyz`: `--volume` now takes a remote OME-Zarr URL itself, `--remote-url` is marked deprecated, and the renderer stops with exit code 1 when `--volume` and `--remote-url` name different sources. AutoPipeline 0.1.3 rendered a remote volume by passing a local cache folder as `--volume` and the URL as `--remote-url`, so on these builds every remote render failed, and with it the render and surface-check steps of a run on a released scan. Every AppImage villa's `latest` release has held since then includes that commit, among them 4eecd08 and 5432721, which 0.1.3's documents name. The self-test and the synthetic demo render local volumes, so they kept passing.

- kit now also reads from the renderer's `--help` whether `--volume` takes a URL. When it does, kit passes the URL there, for renders and for the surface check's seating renders alike; older builds keep the cache folder and `--remote-url`. Either way, fetched chunks still go to VC3D's shared remote cache. `python -m kit vc3d call status` shows which form the renderer takes (`volume_url`). A tool probe saved by 0.1.3 lacks that field and is made again, and a probe that failed (a timeout, say) is never reused: the next call that needs it reads the help again, and `python -m kit vc3d call selftest` always does.
- The commands `kit/plan.py` prints follow villa's current ink detection tutorial (`--volume s3://...`), with a note for builds before 12 October 2026.

Checked on 15 October 2026 against villa's AppImage ccb4318 (sha256 `1a38d4fe480d7bf18d57f8a958af2f6972965f5c8fc6d3b2e18421fb9e270437`): the renderer refuses 0.1.3's arguments with exit code 1 and accepts 0.1.4's past that check, kit's probe reports `volume_url: true`, and `python -m kit vc3d selftest` passes with all five tools. A full remote render of a released segment through AutoPipeline has not yet been run with 0.1.4. The probe was read with the first draft of this fix; the later changes (a failed probe is not reused, help that names `--volume` but no `--remote-url` counts as the URL form, and the cache is written whole) were tested against the stand-in renderer only.

Files: this `CHANGES.md` (rewritten for 0.1.4), `autopipeline/README.md` (one paragraph about the Docker check), `autopipeline/kit/vc3d_agent.py`, `autopipeline/kit/plan.py`, `autopipeline/kit/vc3d_catalog.py` (its description only), `autopipeline/pyproject.toml` (version 0.1.4), tests in `autopipeline/tests/test_vc3d_agent.py` with a stand-in renderer in `autopipeline/tests/vc3d_fakes.py` that behaves like the new build. The new tests include a control: 0.1.3's arguments fail on the stand-in, and the render and surface-check tests fail when 0.1.3's code is put back.

## A monitor snapshot keeps no piece of the run folder's path

The README says a snapshot (`python -m kit autopipeline monitor RUN --snapshot FILE.html`) leaves out your folder's path. On 15 October 2026 a snapshot of the synthetic demo still held part of it. kit's progress lines keep only the last 200 characters of a tool's newest log line (`vc_render_tifxyz: 30 s; ...`), and when that cut lands inside a path, what is left no longer matches the whole path the monitor replaces with `<run>`. The same can happen at the other end, where a long log line is cut at 2,000 characters. The snapshot also showed the full paths of files beside the run folder, such as the demo's stand-in ink model, which name the folders around it.

- The monitor now shows such a piece of the run folder's, the kit home's or the home folder's path as `<run>`, `<kit>` or `~`, like the whole path. A piece counts when it holds a separator after its first character, so it names at least one folder above its last.
- A snapshot, and the page's JSON export, show any other absolute path by its last name only (`.../fake_ink_model.py`), and so a piece of one where a progress line's cut starts (`python: 0 s; .../python ...`, where the cut could start inside a Python under your home folder). URLs such as `s3://...` are kept. The live page on 127.0.0.1 still shows those paths whole.

Files: `autopipeline/kit/autopipe_monitor.py` and its test in `autopipeline/tests/test_autopipe_monitor.py` (it fails on 0.1.3's monitor), and one README sentence.

## Private lists stay out of tracked folders on a Mac

A triage list on a scroll without published labels is private: AutoPipeline writes it only into a run folder git ignores. On a Mac that check could fail open. macOS's `/tmp` and `/var` lead into `/private`, and when the run folder and the kit home were spelled through different sides of such a link, kit judged the run folder to be outside the kit home and wrote the list into a folder git tracks. kit now compares real paths, so a folder git tracks is refused whichever way the path is spelled; the monitor's own folder check compares real paths too. A new test builds a kit home behind an explicit symlink, so it fails on 0.1.3's code on any system.

Three other tests failed only on a Mac and now pass there: the local HTTP test server's listen backlog is larger (macOS refused connections past 5, the audit retried, and its request count came out high), and the MCP test's status call uses a stand-in ink Python (with torch installed the ink probe takes longer than the 3 seconds a piped session's calls get after its input ends). On a Mac with Python 3.14, 0.1.3's tests fail these four and 0.1.4's pass.

Files: `autopipeline/kit/vc3d_agent.py`, `autopipeline/kit/autopipe_monitor.py`, tests in `autopipeline/tests/test_vc3d_agent.py`, `autopipeline/tests/test_vc3d_audit.py` and `autopipeline/tests/test_vc3d_mcp.py`.
