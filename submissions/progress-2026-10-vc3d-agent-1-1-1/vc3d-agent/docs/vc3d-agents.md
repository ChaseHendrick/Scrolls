# Driving VC3D as an agent

Checked 8 October 2026 with villa [`e0bbb8b`](https://github.com/ScrollPrize/villa/commit/e0bbb8b40a2db58b1d71864f286eb85717e59e64). An AI agent can run the VC3D pipeline here with no display: find public data, trace a surface, check that it sits on a papyrus sheet in the right frame with its normal the right way round, audit the volume for missing chunks under it, render its surface volume, flatten it, run ink models with their controls, ask whether a window could show ink at all, and look at every result as a PNG. The same tools come three ways (the seven `lasagna_*` tools, which run villa's lasagna surface fit headless, are described in [lasagna-agents.md](lasagna-agents.md); with AutoPipeline installed, `umbilicus`, `seeds`, `distortion` and `autopipeline` are four more, described in its README):

| Route | Start it with | Use it for |
| --- | --- | --- |
| MCP server | `python -m kit vc3d mcp` (stdio) | Agents with MCP (Claude Code, Claude Desktop, others): typed arguments, progress, cancellation, images |
| Shell | `python -m kit vc3d tools`, `python -m kit vc3d call TOOL '{...}'` | Agents with only a shell, scripts, scheduled runs |
| The VC3D app | the `app_*` tools, or villa's own MCP server through `python -m kit vc3d app-mcp` | What only the app does: interactive growth and editing, points, viewer screenshots |

Each tool takes a JSON object and returns one. The `guide` tool serves this file one section at a time (`{"topic": "ink"}`), and the MCP server also offers it as the resource `kit-vc3d://docs/vc3d-agents.md`. How to build the VC3D tools, and the evidence behind the rendering conventions, are in [vc3d-headless.md](vc3d-headless.md).

## Setting up

You need the VC3D command line tools ("Where to get the tools" in [vc3d-headless.md](vc3d-headless.md)) and this repository. The server and the tools are standard-library Python. Ink models and the detectability probe run in a Python that has numpy and torch, named by `KIT_INK_PYTHON` (plus villa's `vesuvius` package for the `villa` engine, and zarr for zarr inputs).

Claude Code, run from the repository root:

```bash
claude mcp add kit-vc3d -e VC_BIN=/path/to/villa/build/bin -- python3 -m kit vc3d mcp
```

Any other MCP client: command `python3`, arguments `-m kit vc3d mcp`, with the repository root as the working directory or on `PYTHONPATH`:

```json
{"mcpServers": {"kit-vc3d": {"command": "python3", "args": ["-m", "kit", "vc3d", "mcp"],
  "env": {"PYTHONPATH": "/path/to/this/folder", "VC_BIN": "/path/to/villa/build/bin"}}}}
```

The repository commits no `.mcp.json`, so sessions on machines without VC3D do not start a server that can only say so.

From a shell, the same tools:

```bash
python -m kit vc3d tools                    # one line per tool; --json gives the argument schemas
python -m kit vc3d call status
python -m kit vc3d call inspect '{"path": "work/vc3d/segments/PHerc0139/20260317000000-w035_2026031718-on-20250728140407.tifxyz"}'
python -m kit vc3d call render @render-args.json --background
python -m kit vc3d call jobs '{"action": "wait", "id": "JOB_ID", "timeout": 600}'
```

`call` prints the result as JSON and exits 0 when the tool succeeded, 1 when it ran and failed, and 2 on bad arguments. Progress goes to stderr.

| Variable | Effect |
| --- | --- |
| `VC_BIN`, `VC_ROOTFS`, `VC_APPIMAGE` | Where the VC3D tools are (otherwise `PATH`, then the macOS app). `VC_APPIMAGE` is villa's release AppImage or the folder it extracts to; its tools start through links to its `AppRun` ([details](vc3d-headless.md#how-to-use-it)) |
| `KIT_HOME` | The folder everything below is written in, and that relative paths are read from (default: the repository when kit runs from a source checkout, otherwise the working directory) |
| `VC_THREADS` | Default OpenMP threads for VC3D (otherwise `OMP_NUM_THREADS`, then the CPU quota) |
| `KIT_VC3D_HOME` | Where outputs, jobs, caches and the model list live (default `work/vc3d` in the kit home, ignored by git) |
| `KIT_INK_PYTHON` | The Python that runs ink models and the probe (default: the server's own) |
| `KIT_ALLOW_MODAL` | `1` lets the `modal` tool rent compute; only the user sets it. The Modal runner that tool starts (`a script of the source repository`) is not part of this release |
| `KIT_VC3D_PROGRESS_SECONDS` | How often a running tool reports progress (default 10) |
| `VILLA_DIR` | A villa checkout, for `python -m kit vc3d app-mcp` |

Call `status` first. It says where the tools are, whether this build knows `--flip-normals`, the last self-test, which ink Python and packages are present, the running jobs and whether the app is up. On a new machine or build, call `selftest` once (about two seconds): it renders and traces synthetic volumes and checks every value (the trace checks the tracer's normal-grid reader against a control grown with grids for a mirror sheet, which must miss the sheet; with its default weights the tracer reads nothing from the volume, so this does not test how it uses a surface prediction, [details](vc3d-headless.md#how-to-use-it)), and `render` copies the conventions it measured into each receipt.

## Workflow

A labeled public segment, end to end, as tool calls. PHerc0139 w035 is a training segment of the released 9 µm models, so this is a pipeline check, not a test of generalization; w045 and the PHerc0841 segments are the fair tests (AGENTS.md glossary).

1. `catalog {"action": "segment", "sample": "PHerc0139", "segment": "w035"}`: the frames it is published in, its surface volume, ink labels, and the volume URLs.
2. `fetch_segment {"sample": "PHerc0139", "segment": "w035", "frame": "20250728140407"}`: the tifxyz in the frame of that volume (under 1 MB).
3. `check_surface {"surface": SEG, "volume": VOLUME_URL, "frame_search": true, "windows": 5, "voxel_um": 9.362, "background": true}`, then `jobs {"action": "wait", "id": JOB}`: does it sit on a sheet across the surface, in this frame, with its normal the right way?
4. `audit {"volume": VOLUME_URL, "surface": SEG, "background": true}`: is every chunk a render along the surface reads in the bucket? A missing chunk reads as zeros, with no error.
5. `render {"surface": SEG, "volume": VOLUME_URL, "preset": "9um", "background": true}`: 28 layers in the team's order, streamed from the bucket. Add `"crop": [x, y, w, h]` to try a window first.
6. `preview {"path": RENDER_ZARR, "mode": "max"}`: look before inferring.
7. `ink {"input": RENDER_ZARR, "purpose": "benchmark", "model": "ink_9um-seed42", "variants": ["f", "r", "s"], "background": true}`.
8. `kit {"args": ["auc", F_MAP, "--control", R_MAP, "--labels", INKLABELS_ZARR, "--mask", SUPERVISION_ZARR]}`: score against the human labels with the reverse map as the control. The map must be on the labels' grid; compare shapes with `inspect` first, or run `ink` on the published surface volume (`kit {"args": ["fetch", "w035", "work/w035_9um.zarr"]}`), which shares that grid.
9. `detectability {"stack": RENDER_ZARR, "purpose": "benchmark", "model": "ink_9um-seed42", "micron_per_pixel": 9.362}`: how faint an ink this window could show.

On a target scroll, step 0 comes first: preregister with `kit {"args": ["run", "init", SLUG, "--scroll", S, "--question", Q, "--readout", R]}` and `kit {"args": ["run", "status", SLUG, "running"]}` before any map exists, then give `ink` and `detectability` `"purpose": "target", "experiment": SLUG`. To trace a surface of your own instead of fetching one, replace steps 1 and 2 with `catalog {"action": "volumes", "sample": S}` (each volume lists its surface predictions) and `trace`. When a segment comes from another scan's frame (`fetch_segment` with `frame`, or `render` with `affine`), run `landmarks` for that pair of scans, with `surface` for the error where the segment is, and `image` to see the CT agree.

## Rules the tools enforce

They are AGENTS.md's hard rules, built in so an agent cannot skip them by accident:

- **No data in git (rule 6).** Everything is written under `KIT_VC3D_HOME` (default `work/vc3d` in the kit home). An `out` or `dest` inside the repository or the kit home must be a path git ignores (`work/`, `experiments/`, `checkpoints/` and the like), or the tool refuses; a kit home outside the source folder that no git repository holds (`KIT_HOME` elsewhere, or the working directory of an installed kit) may take any path. The source folder takes only the ignored folders, even in a copy with no git. When git cannot answer for another reason (a repository it will not read, say), the tool refuses.
- **Preregister before looking (rule 3).** `ink` and `detectability` with `"purpose": "target"` need `experiment`, a ledger record that passes `kit run check` and is `planned` or `running`. Their output goes under `experiments/<slug>/`, and `ink` adds its command and file hashes to the record. `preview` refuses a file under `experiments/<slug>/` whose experiment has no record.
- **Every check must be able to fail (rule 4).** `ink` with purpose `target` or `benchmark` always makes the reverse-depth map next to the forward one; add `s` for the depth-shuffled control. `check_surface` with `frame_search` reports the margin of the best frame over the next.
- **An ink map is model output, not a reading (rule 2).** Results say so. Never write that letters were found or read.
- **Nothing outward without the user (rules 1 and 8).** `modal` refuses unless the user started the server with `KIT_ALLOW_MODAL=1`. The network tools only download, anonymously. Target maps, previews, triage lists and verdicts stay in the ignored folders and this private workspace: never put them in an issue, a pull request, a forum, Hugging Face or the public Scrolls repository.

The tools cannot tell a target from a benchmark: `purpose` is your declaration.

## Rendering conventions

What `render` does by default, and why:

- **Layer order.** VC3D's normal is N = dP/dcol x dP/drow, and without `--flip-normals` the layer index grows along +N. villa's source says that for the standard segment orientation this normal points out of the scroll and that `--flip-normals` (layer index growing toward the scroll center) "is usually what we want" ([vc_render_tifxyz.cpp](https://github.com/ScrollPrize/villa/blob/e0bbb8b40a2db58b1d71864f286eb85717e59e64/volume-cartographer/apps/src/vc_render_tifxyz.cpp), lines 1297 to 1304; Sourced fact), and tutorial 5 says the flag reproduces the depth order of the published renders and the training labels ([tutorial5](https://scrollprize.org/tutorial5); Sourced fact). So `render` defaults to `"order": "team"`, which passes the flag; on a binary without it (the published container image) kit reverses the layer files itself, which the self-test found identical byte for byte. A mesh whose rows or columns run the other way flips the order silently (Interpretation; notes), so when an umbilicus is known (`umbilicus`, or the catalog's for an open-data volume) `render` does not take "usually" on trust: it votes on the surface's normal sign first (see "Normal orientation"; over the cropped patch when `crop` is given) and passes the flag only when +N points away from the center. A surface whose +N points toward the center renders in team order without the flag, and one with no clear sign is refused (`"orientation_check": false` overrides). The result and the receipt carry the vote. With no umbilicus the flag goes unchecked and the result says so. Either way the reverse control is never optional.
- **Presets.** `9um`: 28 layers (the published 9.362 µm renders; `ink_9um`, Reader v2, v8in). `2um`: 109. `1um`: 116. `legacy`: 65 (the 2023 papers). One voxel between layers.
- **Sampling.** Trilinear: layers half a voxel apart through a steep ramp come back with the interpolated values, not the nearest voxel's (self-test `render_trilinear`).
- **Pixel registration.** Output pixel p samples the surface (p + 0.5) / scale voxels from its first grid point, at pixel centers, and the outer half grid cell of every surface edge renders empty (self-test `render_registration`). Output width = grid columns / meta scale x `scale_segmentation` x `scale` / 2^`level` (times the cube root of an affine's determinant), rounded; height likewise with rows.
- **Frames and levels.** A tifxyz is in the coordinates of the volume it was traced on. The catalog publishes many segments in other volumes' frames too (`fetch_segment` with `frame`) and lists the affine transforms between a sample's volumes (`render` takes `affine`). A level-0 mesh on a 4x binned volume needs `"scale_segmentation": 0.25`; `level` picks the pyramid level to sample. `check_surface` with `frame_search` tells you when a surface is in the wrong frame.
- **Remote volumes.** VC3D streams only the chunks it touches and keeps them in its own persistent cache (below). Renders from URLs retry twice by default, resuming a zarr output. Missing chunks render as zeros without a warning ([test_render_fetch_failure.py](https://github.com/ScrollPrize/villa/blob/main/volume-cartographer/core/test/test_render_fetch_failure.py); Sourced fact), so `audit` the volume under the surface and look at a render before trusting it. S3 volumes reach VC3D through kit's local relay, and the chunks VC3D cached as empty are checked after every run: see "False 404s and VC3D's chunk cache".
- **Outputs.** `"format": "zarr"` (default): an OME-Zarr group whose level 0 is (layers, height, width); `tif`: a folder of `00.tif`, `01.tif`, ... (v8in's input); `both`. The zarr compressor defaults to blosc when numcodecs is installed here, otherwise gzip, which the standard library reads. `composite` gives one image (max, mean, median, alpha or Beer-Lambert over a layer range) instead of layers.
- **Receipts.** `render`, `trace`, `flatten`, `audit`, `ink` and `detectability` write `receipt.json` with their output: the arguments, every command line with its exit, input fingerprints, the kit commit and the machine. A render's receipt adds the layer order, the orientation vote behind it and the conventions the self-test measured.

## Tracing

`trace` runs `vc_grow_seg_from_seed` on a **surface prediction** volume (a model's map of where sheets are, 0 to 255), not on the CT. `catalog {"action": "volumes", "sample": S}` lists each volume's surface predictions. The volume may be a local zarr or a URL.

| Mode | What it does | Needs |
| --- | --- | --- |
| `seed` (default) | Grows a new surface from a point | `seed` [x, y, z] in level-0 voxels, or none for a random seed |
| `resume` | Grows an existing surface for more generations | `resume` (tifxyz) and `generations` above the surface's own count |
| `gen_neighbor` | Casts rays along the normals and builds the next sheet in or out | `resume` (the starting surface), `neighbor_dir` `in` or `out` |
| `expansion` | Grows over a folder of existing segments | `out` holding them |

`params` passes any other tracer parameter, merged last (`generations`, `step_size`, `min_area_cm`, and the rest of villa's `vc_grow_seg_from_seed` JSON). The tracer drops surfaces smaller than `min_area_cm`, so set `"params": {"min_area_cm": 0}` for small tests. `voxel_um` sets the voxel size for areas in cm² when the volume has no metadata. Threads default to min(4, CPUs): villa's own note measured the wall time per cm² lowest at 4 threads on an 8-core and a 16-core machine, with unbounded threads costing 2.2x and 3.5x ([vc_grow_seg_from_seed.cpp](https://github.com/ScrollPrize/villa/blob/e0bbb8b40a2db58b1d71864f286eb85717e59e64/volume-cartographer/apps/src/vc_grow_seg_from_seed.cpp), lines 607 to 613; Sourced fact).

**Seed check.** The tutorial has a person pick a seed on the prediction overlay; the tracer itself only prints the value at an explicit seed and grows from it anyway. So `trace` first runs `seed_check` on an explicit seed: the prediction's trilinear value there must reach 128, the tracer's own threshold for its random and expansion seeds (Sourced fact, [vc_grow_seg_from_seed.cpp](https://github.com/ScrollPrize/villa/blob/e0bbb8b40a2db58b1d71864f286eb85717e59e64/volume-cartographer/apps/src/vc_grow_seg_from_seed.cpp)). A seed off the prediction is refused with the nearest voxel on it within 8 voxels; `"snap_seed": true` moves the seed there once and rechecks prediction and CT at that effective point. The result keeps `moved_from` and the original check in `before_snap`; top-level `seed_check` describes the point passed to the tracer. An unreadable, off-prediction or CT-air recheck stops tracing without another snap. With `ct` (the CT in the same frame) a seed is also refused when the CT says air: 0 (outside the scan or its mask), or below the midpoint of the 10th and 90th percentiles of a box 12 voxels either side. A box with under 15 gray levels of contrast is `unclear` and passes. `"seed_check": false` skips the check. `seed_check` on its own answers the same question for any point. With `"horizon": true` it also reports the growth-horizon triage of villa PR #2047 (Community report, open on 12 Oct 2026; rewritten here, not copied): the share of nonzero prediction in shells over the 65-voxel cube around the seed (the last shell is everything beyond 24 voxels), a class (SEED_VOID, SPARSE_REGION, TRAPPED for a seed on an isolated blob, HEALTHY) and an edge flag within 24 voxels of a face. It is report only, never changes `ok`, and its thresholds come from one PHerc1203 level-2 crop, so treat them as untested here.

The result lists each new surface with its grid, valid fraction, bounding box and area. `name` writes the surface into `out/name` instead of a timestamped `auto_grown_*` folder. A traced surface is model output too: automatic tracers wander between sheets, and that, not compute, is what limits reading. Check every surface with `check_surface` before rendering it, and remember that the seating test looks at one window.

**Areas of large grids.** A grid of more than 2,000,000 vertices is read at every `sampled_every`-th row and column, here and in `inspect`, `check_surface`, `flatten`, `fetch_segment`, `merge_patch` and `merge_surfaces` (AutoPipeline's `render.trim` compares two such areas). A sampled grid's area leaves out two partial strips of cells: the last rows of cells that do not fill a whole step, and the last such columns. Together they are at most `sampled_every` / rows + `sampled_every` / cols of the grid's cells, which on an evenly spaced grid is the share of its area. On such a grid `valid_vertices` counts each vertex read as the block of vertices it stands for, so a fully valid grid gives rows times cols; until 9 Oct 2026 each counted as `sampled_every` squared, which could exceed the grid's vertex count.

**Normal-grid record.** With `normal_grids` the result has a `normal_grids` record: `files` is the number of grid files in the folder after the run, which for a URL is the shared cache, so the total over every trace of that grid set so far, not this run's. For a URL only, `files_before` and `files_fetched` give the cache's count when the run started and what it gained during the run (a trace of the same grid set running at the same time adds to it too); a local folder's record keeps `source`, `remote` and `files` alone. Neither `files` nor `files_fetched` counts the `refetched` files, which reach the cache after the count. `missing` counts the 404 markers the run left, `false_missing` those the bucket holds after all (removed), and `fetch_failed` the grid files VC3D logged it could not fetch (`normal-grid fetch failed for ...` or `normal-grid fetch for ... returned HTTP ...`, villa `core/src/NormalGridVolume.cpp`), with `refetched` and `refetch_failed` for the second try into the cache.

## Checking a surface

`check_surface` answers "can this surface be trusted?" in four parts, and its `verdict` is `ok` only when none finds a problem:

1. **Grid sanity.** Under 5 % valid vertices, or grid edges over 4 times the median length (spikes and jumps), are findings.
2. **Self-intersections.** `vc_tifxyz_selfcross` counts transverse crossings, where the trace passes through itself.
3. **Normal orientation** (given `volume` or `umbilicus`, when an umbilicus is known): the vote in "Normal orientation". No clear sign is a finding, and so is +N pointing toward the center, which only means `render` leaves out `--flip-normals` for this surface and a stack rendered with the flag is reversed.
4. **Seating** (given `volume`). A stack of 2 x `half_layers` + 1 layers is rendered over a `window` (default 192 px) around the surface's central vertex. `half_layers` defaults to about 280 µm either side, so the stack reaches the neighboring windings at any resolution: 30 layers at 9.362 µm, 117 at 2.4 µm, and 30 when the voxel size is unknown (it comes from `voxel_um`, the catalog, or the size in an open-data volume's name). On a seated surface the center layer is papyrus and the layers about a gap away on both sides fall between windings, so the center is brighter than both. The gap is found from the brightness profile itself; `contrast` is the center minus the mean of the two layers a gap away, over the pixels whose center is material (above `material`, default 40); `score` is contrast x coverage, or -1 when under 25 % of the window is in material. Ported from [axiosdevs/herculaneum-scroll-tools](https://github.com/axiosdevs/herculaneum-scroll-tools) `ink/seat_mesh.py` (MIT).

`seated` means a contrast of at least 10, `not seated` at most 3 or a score of -1, and `unclear` between. Those thresholds are an interpretation, not the original's; compare frames rather than trusting one number. With `"frame_search": true` the stack is also rendered at `scale_segmentation` 2, 4, 0.5 and 0.25: a surface in the wrong frame (another scan or binning) scores higher elsewhere, which is reported as `better_frame`, and `margin_over_next` says how clearly the best frame wins.

The result also carries the original's `sheet_contrast` (the middle layer against the layers 25 out). At 9.362 µm it can mislead, since 25 layers can reach the next winding: on w035 it preferred the wrong frame (see "Measured on public data"). Use `contrast` and `score`.

**Several windows.** One window shows one place, and a trace can be seated there and switch sheets elsewhere. `"windows": N` (up to 25) scores the central window and N - 1 more spread over the surface's valid vertices; `seating.windows` lists each one's grid row and column, xyz, pixel window and verdict. The verdict is `seated` when every window is, `partly seated` when some are (the others show where the trace leaves its sheet), `not seated` when every window is not seated, and `unclear` otherwise. Frame search uses the central window.

**S_local** (`"s_local": true`; exploratory). The sheet-profile score from the community notes (Community report): the median, over 40 random columns about 0.3 mm square spread across the windows, of (max - median) / median of the column's mean depth profile, smoothed over about 10 µm and cut to ±131 µm of the surface. A trace on a sheet gives a sharp peak; one between sheets gives a flat profile. Here the same w035 surface scored 0.37 at 9.362 µm and 1.25 at 2.399 µm, so compare surfaces of one scan only, and never treat it as a pass mark. It needs the voxel size. With it the defaults become 9 windows and a window wide enough for two columns (314 px at 2.4 µm); `seed` fixes the columns.

**Trimming over empty CT.** A render over CT zeros is blank there whatever the ink, so a blank-looking map over them means nothing. `trim` copies a surface with every vertex over CT value 0 made invalid (x = y = z = -1), plus `dilate` grid cells around each, updates `meta.json`'s bbox and crops the copy to its valid cells with `vc_tifxyz_trim`; the original is never changed. `level` picks the CT pyramid level tested by nearest voxel (a coarse level reads few chunks; masked volumes omit empty chunks, which count as zero). Over half the surface trimmed gets a note: check the frame first.

**A local volume's meta.json.** VC3D reads `meta.json` next to a zarr, and `metadata.json` only when there is no `meta.json` (villa `core/src/Volume.cpp` 1027-1067); without either it makes one up with voxel size 0, so the tracer cannot apply `min_area_cm` and the app does not list the volume. `volume_meta {"volume": V, "voxel_um": 2.4}` writes `meta.json` from level 0's header (type `vol`, width, height, slices, voxelsize). It never changes an existing file. A `metadata.json` VC3D refuses still gets a `meta.json` beside it, which VC3D then reads instead: one with no `scan` key (the published surface predictions carry such a file, and VC3D throws on it, 1037-1040), a `scan` that is not an object, no type `vol`, no uuid, width, height or slices, a format other than `zarr`, so that VC3D opens no zarr level (1154-1155; a `metadata.json` that names no format counts as `zarr`, 1046-1048), or sizes that do not fit level 0's shape padded by less than one chunk (1146-1150, 1232-1263). The files are parsed as VC3D parses them: a leading byte order mark is skipped, and NaN, Infinity or a number that overflows a double makes a file not JSON. A `metadata.json` VC3D opens is left alone, and so is any existing `meta.json`, even one VC3D refuses (a `meta.json` that names no format is refused); the result's `villa_refuses` gives the reason when VC3D would refuse what is there. A `metadata.json` VC3D opens but that gives no voxel size by villa's rules (a positive `voxelsize`, `voxel_size_um`, `voxelSizeUm`, `pixel_size_um`, `pixelSizeUm` or `resolution_um` at its root, `scan.voxelsize`, an acquisition record, or a `source` record with its level; `core/src/VoxelSizeMetadata.cpp` 190-242) gets a note: VC3D then uses 0, so write a `meta.json` beside it by hand. For remote volumes `trace`'s `voxel_um` does the same job.

**Stitching a patch.** `merge_patch` wraps `vc_merge_patch`: the child's rim is aligned to the parent (RANSAC similarity, then a thin-plate warp) and blended, and its interior replaces the parent there. The villa tool overwrites the parent in place, so the agent tool copies the parent to `out` first and merges into the copy. Villa finds the rim by a distance transform to the child's invalid cells and does not count the grid's own edge, so a child valid out to its edge has no rim and is refused ("child border is empty"); the tool then runs on a copy with one ring of invalid cells added and says so in `child_ring`. Anchors come only from the rim (`border_cells` wide), so keep it narrower than the distance from the child's edge to the part being replaced: a rim that reaches a bad region pulls the child onto it. Run `check_surface` on the result.

**Merging several surfaces.** `merge_surfaces` wraps `vc_merge_tifxyz`, the N-surface merge: give the surfaces as a grid in `rows` as they sit side by side (`null` for a gap); grid neighbors are the edges it aligns, and the grid must be connected. The villa tool wants a volume package (a `merge.json` and a `paths` folder), so the agent tool builds one in its work folder with links to the inputs, and the merged surface lands there as `<first>_merged`. Inputs never change. Surface folder names must be unique, since the villa tool names surfaces by them. It aligns surfaces in the grid (u, v) and blends them; it does not move one onto the other in 3D, so two traces that disagree in depth come out blended between them.

**Checked on a real trace** (PHerc0139 `recto-090` prediction, an 82 by 82 vertex trace at 20 voxels per cell, villa `e0bbb8b`, 8 October 2026; Model output):

| Test | Result |
| --- | --- |
| `merge_surfaces`, the trace cut into two halves sharing 22 columns | merged, 6,004 of 6,084 vertices; within 0.9 voxel of the original surface everywhere (p50 0.47) |
| Same, right half moved (3, -2, 6) voxels plus 0.5 voxel noise | found the 30-column grid offset (t = 30.17, 1,625 of 1,625 inliers); result lies between the two placements (within 7.2 voxels of the original) |
| Control: halves with no shared columns | refused, edge dropped, exit 1 |
| Control: right half moved 20 voxels in z | refused, edge dropped, exit 1 |
| `merge_patch`, parent with a 22 by 22 cell region pushed 6 voxels along z, child a 42 by 42 crop of the original | refused until the child had a ring of invalid cells (now automatic); with `border_cells` 8 the pushed region's normal error fell from 5.9 to 0.9 voxels (max 1.2), and nothing outside the child moved |
| Same with the default `border_cells` 16 | the rim reached the pushed region: error 2.2 voxels (max 4.3) |

An earlier try (two traces seeded about 1 mm apart, and one seeded near the other's edge) found them on different sheets or sharing about 280 vertices, and both tools refused, as they should: cutting one trace is what gives a known answer.

**Phantom prediction.** Surface predictions from patchwise inference spill past the CT mask: `phantoms {"volume": PRED, "ct": CT}` counts prediction voxels (at or above 128) where the CT is 0, in cells of one level-0 prediction chunk at whatever `level` it scans, and flags each cell holding them `edge` (CT in the cell, the rim of the mask), `halo` (CT one cell away, the blend halo) or `beyond` (no CT within a cell, which a blend halo cannot explain: check the two volumes share a frame; it gets a warning). Do not seed a trace in halo or beyond cells, and trim a surface grown there. Community report). On PHerc0139's `recto-090` prediction against the 9.362 µm masked CT at level 4 (176 chunks, about 4 minutes): 0.14 % of prediction voxels phantom, 141 halo cells (0.11 % of prediction cells), none beyond (Model output, 8 October 2026). The tests carry the control: CT that covers everything gives no phantoms, and a prediction two cells past the CT is flagged `beyond`.

**Which frame is a mesh in?** `frame` scores candidate frames without rendering: up to 3,000 vertices from a central window of the grid are mapped into each candidate (`scale_segmentation`, then an affine when given, normals by its inverse transpose), the CT is sampled along each normal chunk by chunk, and the stack is scored as `check_surface` scores seating. Scans differ in brightness and contrast, so across scans the ranking uses `relative_score` (contrast over the spread, 90th minus 10th percentile, of the values sampled, times coverage); `per_volume` ranks one volume's frames by raw score. A candidate with under half its points over nonzero CT is `mostly off the CT` and scores -1. The best is `clear` only when it is at least 1.5 times the runner-up; a mesh that seats nowhere says so. `check_surface`'s `frame_search` still renders with VC3D and tries scales only.

On the PHerc0139 trace above (traced on the 9.362 µm `20250728140407` scan's prediction), `catalog_from` that scan with scales 1, 2 and 0.5 gave 12 candidates (2,304 points, about 15 minutes; Model output, 8 October 2026). Scale 2 and two catalog matrices put it outside their volumes, and scale 0.5 left 81 % of points over CT zero: all rejected. Through the catalog matrices into four 2.4 µm and 1.1 µm scans it was `seated` (contrast 10.8 to 16.6), and in its own scan at scale 1 only `unclear` (contrast 4.7), so the overall call was `unclear`. That is the expected shape: a correct trace seats in every scan the catalog registers to its own, so `frame` rejects wrong frames well but cannot pick one registered scan over another, and the 9.362 µm scan's low sheet contrast makes its own frame score lowest. Two matrices (`20260102150214` and `20260930100252`) gave identical numbers. Use it to rule frames out, and `check_surface` in the chosen frame.

## Normal orientation

`orientation` says which way a surface's normal points. VC3D stacks layers along N = dP/dcol x dP/drow. villa's standard segments (rows along +z, columns turning around the axis) have N pointing out of the scroll, which is why `--flip-normals` gives the team order. A grid with its rows or columns the other way, or transposed, has N pointing in, and the same flag then stacks its layers away from the center with no error anywhere.

The vote: at each sampled vertex, cos = N · r / (|N| |r|), where r runs horizontally from the scroll's center at that vertex's height to the vertex, and the vertex votes outward or inward with the weight area x |cos|. Vertices within 20 voxels of the axis, and normals within about 12 degrees of it, do not vote. `outward_share` is the outward weight over the total; `confidence` is `clear` at 0.8 or more either way, `weak` from 0.65, and `ambiguous` below (thresholds are an interpretation). The center is, in this order: `umbilicus` (a file or URL in villa's formats: text lines z, y, x, or its JSON forms; `umbilicus_scale` for one annotated at another binning), the catalog's umbilicus for `volume`, `centre_xy` (a fixed vertical axis), or a circle fitted to the surface (an estimate, marked unreliable under a 30 degree arc or a poor fit). The catalog has umbilici for some volumes only: on 8 October 2026 PHerc0139's 2.399 µm volume had one and its 9.362 µm volume did not.

The result also says which way the rows run (`+z`, `-z` or across z) and the columns turn, the layout against villa's standard (mirrored, turned, transposed), `folds` (neighboring sampled normals more than 90 degrees apart) and `disagreeing_tiles` (tiles of the grid that vote the other way, in grid rows and columns; `tiles` per side). A surface that folds over itself has no single sign, so decide one sign per patch: `grid_box` row0, row1, col0, col1) votes on one part of the grid, and `render` with `crop` votes on the part its crop covers.

## Zarr integrity

`audit` asks whether a zarr volume is whole where a surface needs it. A chunk missing from the store reads as the array's `fill_value` (usually 0) with no error, in VC3D and in zarr libraries alike, so a blank render or a null ink map over a missing chunk means nothing. Masked volumes leave out empty chunks on purpose, so a missing chunk counts only where a render reads.

- **Headers.** Every pyramid level has its `.zarray` or `zarr.json`, the shapes agree with the multiscales scale transforms, and the dtype, chunks, codec and fill value are reported. zarr v2 (dot or slash keys) and v3 (including sharding) are read.
- **Levels.** Each level holds some chunk (an S3 listing, or a 3 x 3 x 3 lattice of probes where the store cannot list), and `decode` chunks per level (default 2) are downloaded and decompressed.
- **Footprint** (given `surface`). Every chunk holding a surface sample, or within `margin` voxels of one (default 60; a 2um render's 109 layers span ±54), is checked at `levels` (default the finest). A chunk is `present`, `missing` (HTTP 404, or no file) or `unknown` (HTTP 403, a network failure, or past `max_requests`). Missing on the surface is a defect, missing only in the margin a warning, and any unknown chunk makes the verdict `incomplete`, never `clean`. Sharded arrays are checked inner chunk by inner chunk through each shard's index.
- **Render** (given `render`). Counts the zero samples inside a rendered stack's footprint, layer by layer; zeros on the center layer, which lies on the papyrus, are the ones to explain.

The verdict is `defects`, `incomplete` or `clean`, written to `audit.json` with a receipt. Requests to remote stores are anonymous and paced (`rate`, default 20 per second); the whole footprint of w035 at 9.362 µm took 4,793 requests.

## False 404s and VC3D's chunk cache

From this project's cloud, on 8 October 2026, S3 answered HTTP 404 `NoSuchBucket` (with its own headers and request ids) for chunks the bucket holds, on 11 to 32 percent of new connections; a connection that got one kept getting them, and HEAD requests never did (Sourced fact for this machine; the cause is unknown and may be the cloud's egress proxy). VC3D takes any 404 for a missing key: a chunk becomes an empty marker in its persistent cache and reads as zeros in every later run, and a metadata key makes the volume fail to open. A fresh 256 x 256 crop render of w035 at 2.399 µm got 4 such markers and 27.7 % zero samples, with no error.

- **The relay** (`kit/s3relay.py`). `render`, `check_surface`, `trace` and `run` give VC3D a local URL (`http://127.0.0.1:PORT/<the volume's path>`) for an S3 volume. The relay asks the bucket again on a new connection after a false 404, passes a 404 on only when S3 says `NoSuchKey`, and answers 503 for a key that keeps failing, which VC3D retries and then reports as an error rather than a hole. An answer cut off partway through its body, an error's body included, is a network failure: the relay asks again and answers 502 after four failures, so a 404 whose S3 code it could not read never reaches VC3D as missing. Its port comes from the bucket's address, so repeated runs share one cache folder. `KIT_VC3D_RELAY=0` turns it off. Results carry its counters in `cache.relay`.
- **The cache check** (`kit/vc3d_cache.py`). Before and after each run on a URL, every empty-chunk marker in the volume's cache folder (`level_L/iz/iy/ix.empty`, `<key>.empty` and `.vc_cache_empty/<key>.empty`) that kit has not already found true is checked against the bucket. A false one is deleted, so the next read fetches the chunk; `render` and the seating windows of `check_surface` run again, up to `cache_reruns` times (default 2); `trace` reports instead (`cache_reruns` default 0). The cache folder is found as VC3D finds it: `remote_cache_dir` in VC3D.ini (`VC3D_CONFIG_DIR`, else `~/.VC3D`), then `/volpkgs` or `/ephemeral`, then `~/.VC3D/remote_cache`, with a folder named by the URL's last part and its FNV-1a hash. `KIT_VC3D_CACHE_CHECK=0` turns it off.
- **`cache_check`** checks a volume's folders on demand (`volume`, including the relay's folders for it), or every folder whose URL kit can name (`all`): run it after VC3D read a remote volume outside kit (the app, a script).
- **kit's own readers.** `audit`, `kit fetch` and the catalog and model downloads ask again after a false 404 and count a key as missing only on `NoSuchKey` (`kit/s3retry.py`). `kit layers` and `kit auc` refuse URLs: fetch the zarr first.

## Cross-scan transforms and their landmarks

The open-data catalog maps each scan of a sample to the others with affine matrices (3 x 4, voxel x, y, z of one scan to voxel x, y, z of the other), each fitted to landmark pairs that someone placed in both scans (`from_landmarks`, `to_landmarks`), and lists every pair of a sample's scans with the path its matrix was derived by (a stored matrix, its inverse, or a chain). VC3D uses that table to show a segment in another scan's frame, `fetch_segment` with `frame` fetches segments carried that way, and `render` takes such a matrix as `affine`. A matrix that is off puts the surface beside its sheet in the other scan, with no error. `landmarks` checks them (`kit/vc3d_landmarks.py`):

- **Against the landmarks.** For each stored matrix: how far it misses its own landmarks, and whether it is their least-squares affine fit; leave-one-out errors (each landmark predicted by a fit to the others: the error between landmarks, since any fit matches the points it was made from and four points fit an affine exactly); the same for a similarity fit (rotation, one scale, translation), which has 7 parameters instead of 12; how flat the landmark set is; the matrix's scale against the ratio of the voxel sizes, its anisotropy and its handedness (a negative determinant means the frames are mirror images, so a surface's normal flips between them: decide its layer order in the frame you render in). Every derived matrix in the sample's table is compared with the composition its path names.
- **Verdicts.** `inconsistent`: the matrix misses its landmarks by more than `tolerance_um` (default 75 µm, half the 0.15 mm thickness of a carbonized sheet), either while a refit fits them (the matrix was not made from them; `affine_refit.matrix` is the fit) or because no affine fits them (a landmark may be misplaced: see its leave-one-out error). `weak`: four landmarks only, or a left-out landmark predicted more than `tolerance_um` off. `consistent` otherwise; `unchecked` with fewer than four landmarks or none. Flags: `mirror`, `scale` and `anisotropy` (over 1 %), `flat` (thinnest spread under a tenth of the widest), `similarity` (a similarity fit predicts left-out landmarks within tolerance where the affine does not; its matrix is in the report), `not_lsq`.
- **At a place.** With `from_volume`, `to_volume` (any pair the table connects, chained hops included) and `at` points or a `surface` in the first scan's frame: the jackknife spread of the mapped position (how far it moves when one landmark is left out; hops add in quadrature), the distance to the nearest landmark, and whether the point lands inside the target volume. It cannot see bends between landmarks; the image check can.
- **The image check** (`"image": true`, one stored transform, or any pair with `at`; `kit/vc3d_region.py`, numpy). Around each landmark (or point) it resamples a cube of the finer scan through the matrix onto the coarser scan's grid at about 4 µm (`work_um`; the coarser scan's own voxel when larger), and correlates it with the coarser scan at every shift up to `search` voxels (FFT normalized cross-correlation, the peak refined below a voxel). The peak says where the CT puts the point relative to the matrix (`offset_um`, in the target frame); with landmarks, `landmark_error_um` is how far the target landmark lies from that place. A peak counts only when it stands `margin` (0.1) above the best correlation more than `exclude` voxels away, since layered papyrus looks alike nearby (`ambiguous` otherwise); points in masked air are `no_structure`. Each template is also matched against the next point's neighborhood (swapped pairs): if those match, the check failed its control and says so. Reads a few chunks per point (14 landmarks of PHerc0139 at 9.362 µm: 145 chunks, 58 s).

## Ink detection

`ink` runs a model on a rendered surface volume (a zarr from `render`, or a folder of layer TIFFs) with no display.

| Engine | Model | Device |
| --- | --- | --- |
| `villa` | villa's flat inference on a `.pth`: `ink_9um` and its drop-in fine-tunes (Reader v2, d9v2); forward and reverse in one run | CUDA or CPU (no MPS path in villa) |
| `torchscript` | A TorchScript export of an ink checkpoint, run by `scripts/vc3d/torchscript_infer.py` (villa's normalization, center crop of the depth, Hann-blended 128 px patches) | CPU, CUDA or MPS |
| `v8in` | A v8in snapshot through `scripts/v8in_run.py` (layer TIFFs, the central 24 layers) | CPU, CUDA or MPS |
| `command` | Your own program: an argv with `{input}` (or `{layers}` for a layer folder), `{output}`, `{reverse}` and `{device}` | Yours |

`models` lists, registers (`add` with `engine` and `checkpoint` or `model_dir`, and optionally `sha256`, the checkpoint's 64 lowercase hex digits, which `ink` passes to `ink.py` as `--checkpoint-sha256`) and removes the models this machine knows; `"model": NAME` then picks one. A checkout may list other names for one model in the model aliases file (`a note of the source repository`, read by `kit/vc3d_catalog.py`): `model` and a plan's `ink.models` then take any of them, a sha256 the file pins is recorded by `add` under any of them and checked at every load, and a plan may not name one model twice. A released copy has no such file, so each name means only itself. `fetch_model` downloads a known one from Hugging Face or a GitHub release into `checkpoints/` (ignored by git), records each file's sha256 (and refuses an `ink_9um`, Reader v2 or d9v2 file whose sha256 is not the one in `scripts/firstletters/readers.tsv`) and registers it: `ink_9um-seed42` and `ink_9um-seed43` (`scrollprize/ink_9um`, step 75,000), `reader-v2` (`domenicor046/reader-v2`, step 40,000), `d9v2` (`TAUIL-Abd-Elilah/pherc0826-first-letters-search`, release `v1.0`, step 12,000), `v8in` (`YoussefMoNader/ink-8um-v8in` at `d89166b`). Downloads only; nothing is ever posted there (AGENTS.md rule 8).

`variants` picks the maps: `f` (forward, the layer order as rendered), `r` (depth reversed: the control a reader of real ink must lose) and `s` (a fixed depth shuffle, `kit.layers.depth_permutation` with `seed`, neither the stored nor the reversed order: the cleaner null). Purposes `target` and `benchmark` must include `f` and `r`. `purpose` is `target` (preregistered, written under `experiments/<slug>/`), `benchmark` (labeled public segments) or `smoke` (pipeline checks). `layers` windows the source layers; each model then center-crops the depth it was trained on. `box` (torchscript) windows the pixels.

The output folder holds `ink_<variant>.tif` (or `.npy`) and `ink.json`: each map's statistics inside the rendered surface (where the middle layer is nonzero) and the forward map compared with each control (`forward_minus_control`, `overlap_iou`, `pearson_r`). A run whose maps cannot be read fails with exit 3, `"status": "failed"` in `ink.json` and its reasons under `failures` (the log says the same): a map with one value in every finite pixel (all zero included), or no finite value, or a forward map identical to a control. A map with a non-finite pixel on the surface fails too (anywhere in the map when no surface mask has its shape), because a mostly NaN map, as an fp16 overflow can write, would otherwise read as less ink; so does a map with one value on the surface, which a dead network gives while tiled inference leaves 0 off the surface, where it skips the empty patches. A GPU run can write all-zero maps and still exit 0, and such a map would read as "no ink"; a constant control would pass any comparison with the forward map (its AUC is exactly 0.5). The tests are exact, over the whole map and over the surface, so a faint map that varies on the surface, with every surface pixel finite, passes; a near copy of a control is left to `pearson_r` and `overlap_iou`. The log's advice follows the reason: rerun a constant or non-finite map on another device or precision; a forward map identical to a control means the engine did not read the control's input (check `{reverse}`, the layer window and the shuffled copy). When the input came from `render`, the result repeats what its receipt says (`render`: level, scale, voxel size, layer order and whether the order was checked) and lists `warnings`: a downsampled level, a scale below one pixel per voxel, an order other than the team's, or a team order not checked against an umbilicus. A forward map that keeps its blobs under reversal or shuffling responds to something other than ink in depth order. With `f` and `r`, `ink.json` also holds `direction`, the readout of `python -m kit dirtrend`: the forward over reversed area ratio at the thresholds 0.5 to 0.9 and whether it grows (`strengthening`), stays (`flat`) or shrinks (`weakening`) as the threshold rises, counted where the input has CT in every layer, with the CT coverage of the box. After freek_cool's readout rule (Community report, Discord, 31 Aug 2026): on labeled in-domain crops the asymmetry grew with the threshold in 6 of 6 series and on PHerc. 1447 it shrank in 6 of 6, while a bare ratio above 1 did not separate them. `flat` and `weakening` mean the forward map is not ink evidence; `strengthening` is necessary, not sufficient. Calibrated on 12 Oct 2026 over 146 forward and reverse pairs of 21 readers on the PHerc0841 crops, it did not track the labels: on all 10 labeled PHerc0841 map pairs whose reverse map scored the higher AUC it still read `strengthening`, and its 3 other calls came from pairs whose forward map scored higher (Model output, [spec). So treat `direction` as a record, not evidence, until it separates on some labeled data. A `blank` call needs CT coverage of at least 0.9 (after inkdx). The warnings also flag a render made from a lossy volcomp copy. On a benchmark, score the maps with `kit auc` (reverse map as `--control`) and `kit hpscore`; on a target, apply the preregistered readout rule and nothing else.

The result and its `receipt.json` keep `device`: the device asked for (`asked`, `cpu` unless the call says otherwise) and the one the engine's output named (`reported`, from a line such as `Using MPS device`, or null when it named none). They can differ: villa's inference took MPS on a Mac when asked for `cpu`. `cpu` also hides CUDA GPUs from the engine.

For scale, on four cloud CPUs `ink_9um` made forward, reversed and shuffled maps of a 640 px crop in 57 s, and v8in took about 5 to 6 s per tile at batch 4 (784 tiles per map at its default stride of 21, 100 at stride 64; stride 64 cost 0.058 of AUC on w045). On a benchmark the labeled AUC decides, not the thresholded counts in `ink.json`: v8in's reversed map has more pixels above 0.5 than its forward map on w045 while its AUC says forward is right. Run anything larger with `"background": true`.

## Detectability

`detectability` asks whether a window could have shown ink if there were any. A null is ambiguous: blank papyrus, a surface off the sheet, a misplaced depth window, a coarse scan and a model out of its domain all look the same. The probe plants synthetic strokes of known contrast (0.35 mm strokes, 2 mm line spacing, following the measured sheet depth) on one face of the sheet, runs the same model again, and reports the smallest contrast whose strokes come back: the **ink lift**, the rise in the fraction of stroke pixels above `threshold` (default 0.5), must reach `margin` (default 0.05). The verdict is `sensitive` (with that `sensitivity`, in CT units) or `blind`, and a null in a blind window says nothing.

It takes the same engine arguments as `ink`, and needs `stack`, `purpose` and `micron_per_pixel`. `face` is `near` (toward layer 0), `far`, or `both` (default; one baseline run serves both). `amplitudes` default to 4, 8, 16 and 32; the model runs once plus once per amplitude and face, nine times by default. `box` defaults to a central 512 px square. `"self_test": true` checks the probe itself with synthetic detectors and no model: a near-face detector is found, a constant model is blind, a far-face detector is missed on the near face and found with both.

Ported from herculaneum-scroll-tools `ink/detectability.py` (MIT). Its author's caveats carry over (Community report): a sensitivity gained by preprocessing is not a sensitivity gained (smoothing a PHerc1451 stack made planted ink easier to find while agreement with PHerc0139's published map fell from 0.858 to 0.448); it does not settle which way to read the layers; and above a contrast of about 32 the test can invert.

## Background jobs

`run`, `trace`, `render`, `flatten`, `check_surface`, `audit`, `kit`, `fetch_model`, `ink` and `detectability` take `"background": true` (`modal` always runs as one). The call returns a job id at once, and the job runs the same tool in a detached process, so it outlives the server and your turn. `jobs` reads them: `list`, `status`, `log`, `wait` (returns when the job ends or after `timeout` seconds, at most 600; call again to keep waiting) and `cancel` (stops the job and the VC3D process under it). A job's files are in `KIT_VC3D_HOME/jobs/<id>/`. A job that `succeeded` ran to the end; its result's `exit` says whether the VC3D step itself worked.

In the foreground, the MCP server sends progress notifications when the client asks for them, a cancelled request stops the tool's subprocess, and a client that disconnects leaves in-flight calls about three seconds before they are cancelled. An MCP client may give up on a long call before it ends, so start anything long in the background.

## The VC3D app

The command line tools cover tracing, rendering and flattening. The app adds interactive work: growing and editing segments by hand, points, fibers, viewers and screenshots. `app_start` starts VC3D with Qt's offscreen platform and its agent bridge (villa `apps/VC3D/agent_bridge/SPEC.md`: newline-delimited JSON-RPC on a Unix socket), detached, one app at a time, logging to `KIT_VC3D_HOME/app/`. `app_methods` lists the bridge methods (120 at `e0bbb8b`; filter with a `prefix` such as `segmentation.`), `app_call` calls one, `app_screenshot` returns the window or a viewer as an image, and `app_stop` stops it. With `display: true`, `app_start` opens the app's window on this machine's screen instead of offscreen (kept DISPLAY and WAYLAND_DISPLAY; on macOS its own window system), still driven over the bridge. `app_open` starts the app when none runs (offscreen, or with `display` in its window), opens a volume package when given, attaches each tifxyz surface with `segments.attach`, activates the first through `segments.list` and `segments.activate`, and takes a screenshot; a surface the app refuses is reported in `calls` and the status reads `partly opened`. The AutoPipeline monitor's console runs it on the chosen surface. Methods change with villa versions, so list them rather than guessing.

villa ships its own MCP server for the app ([tools/vc3d-mcp](https://github.com/ScrollPrize/villa/tree/main/volume-cartographer/tools/vc3d-mcp)). `python -m kit vc3d app-mcp [--villa DIR] [-- ARGS]` starts it with the app offscreen and the headless environment; its first start installs the `mcp` package. Register it with a client the same way as the kit server. Use one or the other for the app, not both at once.
