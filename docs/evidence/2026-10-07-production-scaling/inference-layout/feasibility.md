# CPU inference layout feasibility

The frozen d9v2 reader has two 3D stem convolutions with depth attention/max pooling, followed by a 2D UNet. Official tiling uses batch 1, patch 128, stride 42, robust per-patch preprocessing and Hann accumulation. The external CPU adapter sets two intraop threads and one interop thread, loads published EMA weights strictly, and keeps fp32, AMP/TTA/compile disabled. Its log shows approximately 71-77 seconds per 196-tile control while earlier input-I/O work measured about 0.34 seconds per map. Model compute is the plausible next target; this is a static attribution, not a new operator profile.

One candidate is the built-in PyTorch conversion `torch.nn.utils.convert_conv2d_weight_memory_format(configured.model, torch.channels_last)`. It only changes 2D convolution weight layout; the 3D depth stem stays in its current format. The official forward functions, data loader, normalization, tile order and accumulator remain untouched. OneDNN may use faster kernels on the available AMD AVX512 CPU. There is no built-in official CLI memory-format switch, so this is an external runtime configuration experiment, not a claimed official feature. Layout can change floating-point reduction kernels and therefore uint8 outputs; exact parity is a mandatory gate, never presumed.

`experiment-plan.json` fixes one 192x192 geometric-center crop from the existing published-control reader inputs, all three depth controls, three alternating pairs, batch 1 and two threads. It estimates approximately 160 CPU-seconds with a 175 CPU-second hard stop. No inference was run. Start only after root GO and reservation of two CPU slots; the current three-agent CPU work must not be oversubscribed. The small crop has nine 128 px tiles per control under the unchanged official scheduler.

A screening pass requires byte-identical TIFF/uint8 maps for every paired control and at least 1.20x median improvement, with every paired ratio above 1.0. Any pixel mismatch rejects exact-output shipping. Even a screen pass needs a separately frozen complete 640x640 matched-control validation and fresh-process timing before deployment. No score/label selection or checkpoint tuning is part of this experiment.

Batch 2 is mathematically sample-independent with instance normalization but may select different convolution algorithms and change uint8 outputs. Threads 1/2/4 and mixed memory-format changes introduce extra factors; they are excluded from this one-factor test. BF16/AMP/quantization and torch.compile have greater numerical/startup changes and are excluded. Prior preloading savings remain too small to call an inference acceleration.
